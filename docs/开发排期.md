## 1. 排期原则

三条原则决定了下面这个顺序，改动前请先理解它们：

**① 按「是否依赖模型账号」切两段，而不是按功能重要性排序。**
DashScope 账号当前 `400 account not in good standing`，所有要真实调模型的活（agent 模式评测、多轮状态机联调）现在做不了。
但核查后发现：**未完成项里大部分是规则层与数据库层的活，不依赖模型**——提示词版本化、注入检测、限流、沉淀去重、PII 脱敏，全都不调模型。
所以把它们全部前置到账号恢复之前，避免干等。

**② 每个 Sprint 必须有可观测的验收标准，不能是"做完即可"。**
本项目的教训是"静默失败最难查"（后台列表空了没有任何报错、提示词 KeyError 被吞成降级）。
所以下面每条验收标准都写成可执行的验证动作，而不是主观判断。

**③ 先补护栏，再堆能力。**
多轮状态机听起来最有价值，但在注入检测、提示词版本化没做之前做它，等于在一个没有护栏的系统上堆复杂度。

当初的任务清单：

2. 新建 `prompt_versions` 表：`version` / `name` / `content_hash` / `content` / `created_at` / `active`
3. `agent_runs` 增 `prompt_version` 列，运行时写入

**验收（已全部实测通过）**：

| 验收项 | 实测结果 |
|---|---|
| 首次同步产生版本 | 指纹 `sys1-plan1-judge1` ✅ |
| 内容未变时重启不产生新版本 | 重复 sync 后指纹仍为 `sys1-plan1-judge1` ✅ |
| 改内容后版本递增 | 追加一行后变为 `sys2-plan1-judge1` ✅ |
| 回滚 | active 变 v3，**内容 hash 与 v1 一致、文件恢复原样** ✅ |
| 运行时落库 | 新轨迹 `agent_runs#26` 的 `prompt_version = sys3-plan1-judge1` ✅ |
| 无回归 | intent 30/30、fixed 30/30，与基线一致 ✅ |

> **回滚语义说明（重要，别按字面理解）**：回滚后版本号是 **v3 而不是回到 v1**，
> 但内容 hash 等于 v1、文件也恢复原样。这是刻意的——
> 若实现成"只把目标版本的 active 置 1"，重启后 `sync()` 会发现文件 hash 与 active 版本不匹配，
> 于是又插一个新版本，**回滚被自动撤销**。所以正确做法是"把历史内容写回文件"，
> 版本号单调递增但内容真正回退。

### 3.3 PII 输入侧脱敏 ✅（2026-10-26 完成）

现状（改前）：只有输出侧红线（`verifier.REDLINES.privacy`），**输入侧与存储侧没有**——用户发来的号码会原样进 `messages` 表和向量库。

**交付**：新建 `app/agent/pii.py`（手机号 / 身份证 15 与 18 位 / 邮箱三类），接入两个写入点：
`service._record_user_message`（对话历史）、`memory.remember`（向量记忆）。
`tools._create_ticket` 里**工单正文保留原文、同步写进 messages 的那一份掩码**——
两份口径不同是刻意的：工单是 HR 的办理凭据，对话历史只是沉淀副产品。

**关键约束**：**只脱敏"写入的副本"，不动当次请求的原文**——
graph 里流动的文本仍是原文，检索与工具调用不受影响。

**验收（实测）**：

| 验收项 | 结果 |
|---|---|
| 6 条含 PII 样本掩码 | 6/6（如 `137****5678`、`110101********1234`、`z***@example.com`） |
| 6 条正常问法不误伤 | 0 误杀（"面试资料包括哪些"、"你好"、"offer 什么时候发" 等原样保留） |
| HTTP 端到端 | 带号码提问 → `messages` 表为 `137****5678`，且回答正确 |
| 工具不受影响 | 紧接着查进度仍返回【已初筛通过】等正确结果 |

**已知边界**：18 位纯数字且日期位合法的串（如某些订单号）会被当身份证掩码——
**规则误杀的代价（把用户原话改得无法处理）高于漏脱敏**，所以取保守覆盖，
银行卡号、住址这类需语义判定的不做，留给后续数据分级方案。

### 3.4 用户级限流 ✅（2026-10-26 完成）

**交付**：新建 `app/agent/ratelimit.py` + `rate_events` 表（只记 `candidate_id` 与时间，不存正文），
按 1 小时滑动窗口计数，默认 30 条/小时；阈值写 `settings.rate_limit_per_hour`，
超管在【模型配置】实时改，**存后立即生效、无需重启**（0 = 不限流）。

> **为什么单开一张表而不是 COUNT messages**：
> `tools._create_ticket` 建单时会往 messages 再插一条 user 消息（工单正文），
> 用 messages 计数会把"一次提问 + 一次建单"记成两次，正常用户被提前限流。
> 计数与存储必须解耦——限流只关心"用户发起了多少次请求"。

**超限不报错**：仍然给答案（改走固定管线），额外外发一条 `notice` 事件提示，
前端在气泡下方与 Agent 过程面板各显示一次。

**验收（实测）**：

| 验收项 | 结果 |
|---|---|
| 阈值改为 2 后连发 5 条 | 第 1、2 条放行，第 3 条起 `rate_limited=true` 且提示可读 |
| 超限仍有回答 | 是（固定管线回答，长度正常） |
| SSE 事件流 | `notice → intent → fallback(rate_limited) → done(mode=rate_limited)` |
| 阈值回写 | 控制台保存后 GET 立即返回新值，无需重启 |
| 窗口滑动恢复 | 清理 rate_events 后恢复正常计数 |

**顺带产出**：新增 `app/run_eval.py` 作为评测统一入口（S4.3 回归门禁的前置），
内置逐条耗时打点，符合"长评测必须落日志"的新约定。

1. **工单号取不到导致重复建单**：`tool_trace` 只记 `{tool,args}` 不含返回内容，工单号其实在
