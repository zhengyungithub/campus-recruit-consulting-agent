## 1. 排期原则

三条原则决定了下面这个顺序，改动前请先理解它们：

**① 按「是否依赖模型账号」切两段，而不是按功能重要性排序。**
DashScope 账号当前 `400 account not in good standing`，所有要真实调模型的活（agent 模式评测、多轮状态机联调）现在做不了。
但核查后发现：**未完成项里大部分是规则层与数据库层的活，不依赖模型**——提示词版本化、注入检测、限流、沉淀去重、PII 脱敏，全都不调模型。
所以把它们全部前置到账号恢复之前，避免干等。

**② 每个 Sprint 必须有可观测的验收标准，不能是"做完即可"。**
本项目的教训是"静默失败最难查"（后台列表空了没有任何报错、提示词 KeyError 被吞成降级）。
所以下面每条验收标准都写成可执行的验证动作，而不是主观判断。

**③ 先补护栏，再堆能力。**
多轮状态机听起来最有价值，但在注入检测、提示词版本化没做之前做它，等于在一个没有护栏的系统上堆复杂度。

### 3.4 用户级限流 ✅（2026-10-26 完成）

**交付**：新建 `app/agent/ratelimit.py` + `rate_events` 表（只记 `candidate_id` 与时间，不存正文），
按 1 小时滑动窗口计数，默认 30 条/小时；阈值写 `settings.rate_limit_per_hour`，
超管在【模型配置】实时改，**存后立即生效、无需重启**（0 = 不限流）。

> **为什么单开一张表而不是 COUNT messages**：
> `tools._create_ticket` 建单时会往 messages 再插一条 user 消息（工单正文），
> 用 messages 计数会把"一次提问 + 一次建单"记成两次，正常用户被提前限流。
> 计数与存储必须解耦——限流只关心"用户发起了多少次请求"。

**超限不报错**：仍然给答案（改走固定管线），额外外发一条 `notice` 事件提示，
前端在气泡下方与 Agent 过程面板各显示一次。

**验收（实测）**：

| 验收项 | 结果 |
|---|---|
| 阈值改为 2 后连发 5 条 | 第 1、2 条放行，第 3 条起 `rate_limited=true` 且提示可读 |
| 超限仍有回答 | 是（固定管线回答，长度正常） |
| SSE 事件流 | `notice → intent → fallback(rate_limited) → done(mode=rate_limited)` |
| 阈值回写 | 控制台保存后 GET 立即返回新值，无需重启 |
| 窗口滑动恢复 | 清理 rate_events 后恢复正常计数 |

**顺带产出**：新增 `app/run_eval.py` 作为评测统一入口（S4.3 回归门禁的前置），

### 4.1 工单沉淀相似度去重（0.5 天）✅

| 项 | 内容 |
|---|---|
| 现状 | `main.py:1063` 勾选"沉淀为知识库"后直接 `INSERT INTO faqs`，无任何查重 |
| 前车之鉴 | FAQ 曾被初始化逻辑重复播种 3 份（15 → 45 条），直接污染检索质量 |

任务：入库前跑一次相似度检索，≥0.9 判为已存在 → 跳过并提示已有相似条目（附条目 id）；0.8~0.9 提示人工确认是否合并。

**交付**：`agent/dedupe.py` + `retrieval.similar_faqs()` / `question_vectors()`。
判据是「问题对问题的语义相似度」与「关键词相似度」取较大值，分三档：
**≥0.92 自动跳过**（只在高置信区自动丢弃）/ **≥0.78 提示 HR 确认** / 其余放行。

**阈值是实测标定的，不是拍的**：用 `text-embedding-v3` 跑了 5 组改写 + 5 组同主题不同意图 + 3 组完全无关，
得到同义改写 0.79~0.99（均 0.90）、同主题不同意图 0.77~0.82、完全无关 0.42~0.60。
关键结论：**「同义改写」与「同主题不同意图」在向量空间里是重叠的，不存在干净分界**——
所以自动跳过只敢放在最高置信区，模糊区一律交给人，这也正是三档设计的理由。

**验收（实测）**：同义改写「面试要准备什么资料？」→ `sim=0.95 via=dense` 被拦下并回传已有条目 #51；
完全无关「公司有没有班车？」→ `sim=0.56 level=ok` 正常放行。

### 4.3 checkpoints.db 清理机制（0.125 天）✅

**交付**：`runtime.prune_checkpoints()` / `ckpt_stats()` / `ckpt_retention_days()`。

**按「整条会话线程」删而不是按「单条检查点」删**：langgraph 的检查点是一条父子链，
每个 checkpoint 通过 `parent_checkpoint_id` 串到上一个。只删链中间的节点会让剩下的
检查点指向已不存在的父节点——将来若接回 HITL 恢复，读到的就是断链状态。
判据因此取「整条线程最后一次活动的时间」。

启动时机：**必须早于任何图调用**——图是懒加载的，一旦被首次请求实例化就会占住
sqlite 连接，那时再做 VACUUM 就回收不了空间了。

阈值走 `settings.ckpt_retention_days`（默认 7，0 = 不清理），超管后台可实时改并手动触发。

**验收（实测）**：注入 60 条 30 天前的过期会话 → 清理后 `deleted=60`、
体积 29236KB → 28992KB，且 441 条近期会话线程一条未丢。

### 4.5 本轮顺带修掉的两个隐患（重要）

排查 agent 基线波动时挖出来的，都不是新写的代码，是**一直存在但被掩盖的 bug**：

| # | 问题 | 影响 | 修法 |
|---|---|---|---|
| 1 | `retrieval.search()` 把 dense 分数**方向搞反**了。原代码 `dense = 1.0 - h.score`，注释写「qdrant 返回的是距离」——**实测完全一致文本的 score = 1.0000**，说明 COSINE 下返回的就是余弦相似度 | hybrid 融合里越相似的条目得分越低，**排序整体反向**：完美匹配排到末尾，噪声条目排到前面。而且高分（dist<0.25）的 dense-only 条目会因 hybrid<0.15 被**整条过滤掉**，等于"最该召回的被丢弃" | 去掉换算，直接用 `float(h.score)` |
| 2 | `retrieval.sync_faqs()` **只 upsert 不 delete** | FAQ 删除后向量仍留在集合里形成**幽灵条目**——实测 20 条 FAQ 对应 52 个点。检索会命中已删除知识，查重更是直接撞上幽灵 | 改为双向同步，先按当前 `faqs` 表清理失效点，再 upsert 变更项 |

**教训**：① 相似度/距离这类"方向型"数值，**必须实测确定语义**，不能靠接口名或注释推断；
② 缓存/索引类结构**只有写入没有回收**时，脏数据会随运行时间单调累积，
表现为"系统越跑越怪"——这类问题在单次测试里看不出来，得靠"库里有 20 条、索引里有 52 个点"这种对账发现。

### 6.3 稳定评测口径 ✅（2026-10-26 完成）

**起因**：42 条 agent 用例连续多轮得分 40 / 36 / 34 / 33，**波动 ±4 条**。
单次通过率不可靠，就没法当门禁——会把正确的改动误判成回归（本轮差点发生）。
拆开看是三类问题，各自独立处理：

| # | 问题 | 处理 |
|---|---|---|
| 1 | 评测会挂起，护栏是假的 | 线程 `join(timeout)` 杀不掉卡在 socket 读的用例（实测卡 1417s）→ 改常驻子进程池 |
| 2 | `must` 用精确串匹配 | 期望"重新上传"、模型答"重新提交"就判缺关键事实 → 支持同义组 |
| 3 | 单次结果无法区分抖动与回归 | 多数投票 + 归因指标分列 |

**① 评测执行器改子进程（`agent/eval_worker.py`）**

原来的护栏用 `threading` + `join(timeout)`，那是**假护栏**：Python 线程无法被强制杀死，
卡在 socket 读（模型/向量请求静默挂起）时，超时后线程仍在，主进程只能继续等。
第3期实测单条卡 **1417s（23.6 分钟）**，而护栏设的是 120s。

- 用 `ProcessPoolExecutor(max_workers=1, mp_context=spawn)` **复用同一个 worker**：
  langchain / langgraph 冷启动实测 13~22s，每条用例起新进程光启动就要 10 分钟。
- 超时后**必须 kill worker 进程**并懒重建：只 `shutdown` 不够，future 还在跑，主进程仍会挂住。
- 附带收益：**Qdrant 本地文件锁的持有者始终是 worker 而不是评测主进程**。
  主进程一旦取过 client 就会长期占锁，之后每条用例的子进程都打不开库
  （第3期被这个锁坑到 22 分钟/条）。
- 留了 `EVAL_INLINE=1` 开关：跳过子进程在当前进程跑，仅用于排查
  （"问题来自被测代码还是进程隔离"），默认不开。

**② `must` 支持同义组**

- 写法：`"must": [["重新上传","重新提交","再次上传"]]`，组内任一命中即算过；
  单字符串仍按单元素组处理，**向后兼容**。
- 约定：**组内第一个元素是原始断言**，后续只是可接受的等价说法 ——
  放宽的是措辞，不是语义。
- 本轮升级了 #10 / #14 / #20 / #21 / #24 五条（原先是精确措辞断言）。
  效果：#14 从"时好时坏"变为稳定通过。

**③ 多数投票 + 归因分列**

- CLI：`python -u run_eval.py agent 0 --repeats 3`；
  HTTP：`POST /api/admin/eval/run` 传 `repeats`（agent 模式默认 3，其余 1）。
- **只对失败用例复跑**（通过的再跑两遍纯属浪费），3 次取 2 通过即判过。
- 新增指标：
  - `single_rate` 首次通过率 vs `passed_rate` 稳定通过率，
    **两者差值就是模型抖动造成的假失败量**；差值大说明这轮数据不宜单独当门禁
  - `flaky_cases` 时好时坏的用例 id 与投票序列
  - `internal_leak_hits` 单独统计"模型把工具名/内部 JSON 回显给用户"
    —— **统计分列，但判定仍算失败**：回显内部实现对用户是真缺陷，
    不能因为"不是检索回归"就放过
  - `retry_used` 触发复跑的用例数

**实测对比（42 条 / repeats=3）**：

| 指标 | 事故版本 | 修复后（run #43） |
|---|---|---|
| 整体通过率 | 69~76% | **92.9%（39/42）** |
| 首次通过率 | 71.4% | **90.5%** |
| 指代还原命中 | 0 | **4** |
| 重复提问识别 | 0 | **1** |
| 内部实现回显 | 1 | **0** |
| 降级 / 异常 | 1 / 0 | **0 / 0** |
| 耗时 | 221s | **147s** |

> 事故版本的低分**不是模型变差，是我自己的改动引入的回归**，见下。

**过程中的事故（同步记入 Handoff §4.4 第 23 条）**：
清理死代码 `_purge_eval_vectors` 时，把**同在 `if prev:` 块里的 `_seed_history(cid, prev)` 一并删掉了**。
后果：所有带 `prev` 的多轮用例拿不到上一轮问答 → 指代还原与重复识别全部失效 →
表现为 `coref_hits=0` / `repeat_hits=0`，且 #34/#35/#36/#40/#41 稳定判负。

排查手法（可复用）：
1. 先 `EVAL_INLINE=1` 跑同一批用例 → **同样失败**，排除"进程隔离"嫌疑；
2. 给 worker 加 `debug` 打印子进程看到的 `messages` 条数 → 是 1 条而不是 3 条；
3. 回看 `_run_one`，才发现播种那行在删死代码时被连带删掉。

**教训**：删"看起来没人用"的代码，要连它所在的**分支上下文**一起看；
删完立刻跑一遍**带 `prev` 的多轮用例**——多轮能力只在这类用例上有覆盖，
intent/fixed 全绿也发现不了。

**遗留（下一步 S4.4）**：仍有 2~3 条用例稳定失败（#17 / #21 / #33），
原因是**模型偶发不调用 `knowledge_search` 就自行作答**（结果无引用）。
规则层已经规划出该检索，执行不该依赖模型"心情"。

### 6.4 让执行不依赖模型"心情"（S4.4）✅（2026-10-26 完成）

**问题**：口径稳定之后，剩下的失败里有一类是**稳定的**——#17 / #21 / #33 连续多轮判负，
症状完全一致：**planner 规则层已经规划出 `knowledge_search`，模型那一步却凭印象直接作答**，
结果无引用、缺关键事实。这是"抖动"里唯一不抖的那一批，也是真实用户最在意的错误：
**问政策，机器人张口就来**。

**方案**：计划的**必做只读步骤**，模型本轮没执行就由框架**自动补执行**，
拿回结果后回灌给模型让它据此重答。

| 决策 | 选择 | 理由 |
|---|---|---|
| 补哪些 | 只补**只读**工具（`knowledge_search` / `get_my_progress` / `list_my_tickets`） | 检索重复执行顶多浪费一次查询；`create_ticket` 会真落一张工单（脏数据、不可撤销），**永不自动执行**——与 `handling` 在 `node_act` 硬拦截建单是同一条原则 |
| 补几轮 | 上限 1 轮（`forced_steps`） | 补执行后仍答不好就不重复折腾，直接交给核验，避免回炉死循环 |
| 怎么回灌 | **HumanMessage + 自然语言**，不是 ToolMessage / 裸 JSON | 上一条 AIMessage 没有 `tool_calls`，挂 ToolMessage 会因 `tool_call_id` 失配被 DashScope 拒绝（第1期踩过）；裸 JSON 会被模型照抄进答案（见下方事故） |

新增 `graph.node_force_act` + `planner.pending_required()` + 计划里 `required` 标记，
图结构变为 `agent → force → agent ⇄ act`。提示词里必做步骤显示为「⬜待办·必做」，
实测这一行提示本身就让部分用例的模型自己调了工具（#17 就是）。

**连带修掉一个真缺陷**：工具返回的 JSON 里带了 `source`（hybrid / dense / keyword 融合模式），
这是**纯内部元数据**，对作答毫无帮助，模型却照抄成「依据条目：xxx（来源：hybrid）」回显给用户。
三处一起改：① 工具返回不再带 `source`；② `internal_leak` 红线补一条**窄口径**规则
（只认 `来源：hybrid|dense|keyword|bm25|vector|qdrant`，不误伤"来源：官方通知"）；
③ 补执行的回灌用自然语言而非裸 JSON。
> 原则：**内部字段一律不进模型视野**——靠模型"别照抄"是拦不住的，源头不给才是根治。

**实测（42 条 / repeats=3）**：

| 指标 | S4.4 前（run #43） | S4.4 后（run #49） |
|---|---|---|
| 整体通过率 | 92.9%（39/42） | **95.2%（40/42）** |
| 首次通过率 | 90.5% | **95.2%**（首次=稳定，抖动清零） |
| 引用率 / 关键事实命中 | 1.0 / — | 1.0 / **0.978** |
| 工具序列符合率 | 1.0 | 0.909 |
| 内部实现回显 | 0 | 0 |
| 降级 / 异常 | 0 / 0 | **0 / 0** |
| 耗时 | 147s | **138s** |

最关键的变化是**失败用例的构成**：#17 / #21 / #33 这三条"稳定失败"全部转通过，
剩下的 #33（工具序列缺 `create_ticket`，flaky）与 #36（缺关键事实）都是**抖动**而非稳定缺陷。
补执行本轮触发 **4 次 / 4 条用例**（`forced_steps=4`），说明约 1 成回答是靠框架兜住才拿到依据的
—— 这个数字本身就是"执行确定性"的度量，应当长期观察，若持续走高说明提示词约束在失效。

> 中间态数据值得记一笔：只做补执行、还没修 `source` 泄漏那轮（run #48）是 92.9%，
> 且出现 1 次降级 + 1 次内部实现回显。**新能力会暴露旧缺陷**——
> 把裸 JSON 回灌给模型，等于邀请它照抄内部字段。
