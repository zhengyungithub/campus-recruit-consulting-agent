# Agent 演进路线（第 0 期 · 第 1 期）

> 更新：2026-10-25
> 目标：把"能问答的流程机器人"逐步改造成"可编排、可自救、可验证"的 Agent

---

## 1. 为什么要分期改

原来的系统是典型的 **L2 编排式问答**：固定管线（意图 → 分派 → 检索/查库 → 拼答案）外加一条可以自行调工具的 LangGraph 支路。
它能答对，但有三个致命短板：

1. **没有度量**：改 prompt / 换模型 / 调规则后，只能"问两句看看"，无法判断变好还是变坏。
2. **没有计划**：复合问题（"我到哪一步了？另外体检要查什么"）会被答一半。
3. **没有兜底**：工具调用失败、模型超时、陷入重复调用时，用户只能看到一个"没生成成功"。

所以改造顺序遵循一条原则：**先能量化，再改结构**——先把评测做出来（第 0 期），
再动主链路（第 1 期），每一步都有门禁。

## 2. 第 0 期：评测地基（已完成）

| 产物 | 位置 |
|---|---|
| 评测引擎（三种力度） | `app/agent/eval.py` |
| 标注集（33 条） | `app/evals/cases.jsonl` |
| 落库与 API | `main.py` 的 `eval_runs` 表 + `/api/admin/eval/{cases,run,runs,runs/{id}}` |
| 前端页面 | `frontend/src/components/AdminEval.vue`（超管菜单【评测回归】） |

三种力度：

- **intent**：只跑意图识别，500ms 内出结果，改规则后秒级验证
- **fixed**：整条固定管线（不建工单），验证现有线上行为
- **agent**：完整 LangGraph，真实调工具，用独立评测账号跑完清理

指标：意图准确率 / 关键事实命中 / 引用率 / 工具序列命中 / 转人工判定 / 核验通过率 / 平均·P95 延迟。
**改任何东西之前先跑一轮存基线，改完再跑一轮对比**，这就是回归门禁。

## 3. 第 1 期：图重构 planner → executor ⇄ act → critic（已完成）

### 3.1 新图结构

```
START → intent → plan ─┬→ clarify（信息不足反问）→ END
                       └→ agent ⇄ act ─┬→ critic → END
                                       └→ degrade（超预算/失败未收敛）→ END
                      critic 未通过且有余量 → 回炉补检索
```

### 3.2 各节点职责

| 节点 | 做什么 | 关键设计 |
|---|---|---|
| `plan` | 把一句话拆成执行步骤 | 默认**规则规划**（零延迟、可解释）；`agent_planner=llm` 时才用模型拆步骤 |
| `agent` | 带清单与失败反馈做一次推理 | 计划 + 已完成打勾 + 失败换路建议一起注入提示词 |
| `act` | 执行工具，失败分类 | unknown_tool / exception / empty_result / duplicate 四类，回喂建议支持一次自救 |
| `critic` | 引用核验 + 决定是否回炉 | 回炉次数与总预算挂钩，不再无限重试 |
| `degrade` | 预算耗尽/链路未收敛时的兜底 | 直接跑固定管线，保证用户永远拿得到回答 |
| `clarify` | 信息严重不足时反问 | 只在**无历史上下文 + 极短/纯指代**句触发，宁少问不多问 |

预算（可在 `app/agent/config.py` 改，也支持环境变量覆盖）：

```
AGENT_MAX_STEPS = 5        # 最多 5 轮推理
AGENT_MAX_TOOL_CALLS = 8   # 最多 8 次工具调用
AGENT_DEADLINE_S = 30      # 单次运行 30s 墙钟上限
```

### 3.3 第 1 期暴露并修掉的真实问题

评测一上手就抓出五个以前只在偶发场景下才看得见的缺陷：

| 问题 | 现象 | 修复 |
|---|---|---|
| 跨轮记忆污染 | 评测用同一账号连跑，前一条答案被灌进后一条上下文，出现"张冠李戴"式回答 | `run_agent(..., use_history=False)`，评测隔离历史，线上仍保留连贯记忆 |
| Embedding 无超时 | 单条用例卡了近 40 分钟，整轮评测报废 | `OpenAIEmbeddings(timeout=20, max_retries=1)`，另给每条用例加 120s 线程护栏 |
| 多次检索覆盖引用 | 一轮里调 3 次检索，只有最后一次的条目进 citations，导致依据被判"编造" | `node_act` 累加并去重所有 `knowledge_search` 结果 |
| 核验只比答案正文 | 回答里引用《条目标题》被判为无依据 | verifier 的 context 同时纳入 question 与 answer |
| 计划清单被当必做清单 | 计划里挂了"可选建单"，知识库答得上的问题也被硬建一张工单 | 计划里不再列可选步骤；提示词明确"自助步骤先给，再问是否需要转人工" |

## 4. 第 2 期：Verifier 升级 —— 双通道核验 + 合规红线（已完成）

### 4.1 为什么必须升级

第 1 期的 verifier 只会做一件事：把回答里的硬信息（数字 / 日期 / 书名号 / 英文缩写）抠出来，
回引用原文逐条比对。它能抓住"编了个日期"，但抓不住三类真正的风险：

| 风险 | 举例 | 旧核验能不能抓 |
|---|---|---|
| 越权承诺 | "放心吧，你一定能被录用" | ❌ 一个硬数字都没有，ratio 满分 |
| 泄露标识 | "联系我 138xxxx" | ❌ 数字在工具返回里出现过反而"有依据" |
| 弱断言 | 整句找不到任何依据，但没写数字 | ❌ 直接跳过 |

### 4.2 双通道设计（`app/agent/verifier.py`）

```
回答进来
   │
   ├─ L1-A 红线扫描（纯正则，零延迟、零成本，最优先）
   │     promise_offer   承诺录用 / 入职结果
   │     invent_schedule 给出依据里没有的具体时间点
   │     privacy         手机号 / 身份证 / 邮箱（本人信息与引用原文除外）
   │     internal_leak   工具名 / JSON / 内部字段
   │
   ├─ L1-B 硬信息比对（第 1 期能力，沿用 items/unsupported 字段）
   │
   ├─ L1-C 句子级引用锚点
   │     逐句拆开，用 2-gram 字面重合度找最相似依据句，标出无依据句
   │     寒暄/过渡/元叙述句（"你当前处于【X】环节"）跳过，不算无依据
   │
   └─ L2 LLM Judge（按需调用）
         - auto（默认）：规则判 pass 就不调模型，省成本省延迟
         - on：每条都裁（语义级：是否答非所问 / 是否无据断言 / 是否越权）
         - off：纯规则
```

**终局裁定优先级**：红线 `block` > Judge `unsupported/off_topic`（fail）> 规则综合（pass/partial/fail）。
红线不接受 Judge 翻案——它是合规底线，不是打分项。

### 4.3 critic 的处置策略

| 判定 | 处置 |
|---|---|
| 红线第 1 次 | 清空答案 + 注入具体违规句与改写建议，给**一次**改过机会 |
| 红线第 2 次 | `redline_blocked=True`，**拒绝放行**，强制降级固定管线兜底 |
| fail（无据） | 回炉补检索一次（`revisions < 1`） |
| pass / partial | 放行 |

### 4.4 实现中踩到并修掉的两个真问题

1. **句子锚点误杀合规回答**：把"你当前处于【已初筛通过】环节，具体结果以官方通知为准"
   判成 fail —— 元叙述句复述的是工具查询结果，本来就不在知识库条目里。
   修法有二：① 把元叙述 / 引导语列入非事实句跳过；② 句子锚点降为**弱信号**——
   硬信息对得上时，单凭句子锚点最高只能压到 partial，把最终裁决交给 Judge，不直接判死。
2. **意图层悄悄依赖模型兜底**：额度耗尽后，有 3 条用例（`我现在处于什么环节`、
   `帮我改一下面试时间`、`我想换个面试站点`）掉到 kb_qa。它们本该由规则覆盖。
   补规则后这 3 条回到 100%，**intent 模式平均耗时从 434ms 降到 53ms**（少一次模型调用）。

| intent | 30 | 100% | 100% | — | — | — | 0 | 0 | 46ms | 7ms |

### 4.6 Judge 上线后发现的两件事（都改了）

第一版 Judge 有独立的否决权：`unsupported` 直接判 fail。上线即翻车：

| 问题 | 现象 | 修法 |
|---|---|---|
| Judge 误伤 | 两条例证充分的合规回答（#22 已建单的改期答复、#32 复合问的完整答复）被判 `unsupported` → fail | 改裁定口径：**Judge 只能"捞回"不能"判死"**，单独说 unsupported 时 status 最多抬到规则已给的等级 |
| Judge 拖垮延迟 | Judge 挂在回炉路径上，每次回炉都要多等一轮模型；P95 冲到 47.9s，平均 17.9s | critic 改**两阶段**：先纯规则决定要不要回炉（零延迟），确定放行时才补一次 Judge 观测 |

配套的 prompt 也收紧了：明确要求"只在找到确凿一处问题时才填 issues，找不到就必须 ok"，
且"依据没逐字复述""回答比依据更精简""寒暄引导语"都不算问题。

另外修了一处评测标注过严：case 10 原本 `must_not: ["工单"]`，而正确答案是"给自助步骤 +
询问是否需要转人工"，句里必然会提到"工单"二字。改成检测真正擅自建单的表述
（`已为你生成反馈工单` / `已提交反馈工单` / `已转人工`），拦截的是行为而不是措辞。

### 4.7 一次真实的外部故障：模型额度耗尽

跑到第 13 条时 DashScope 报 `403 Free quota exhausted`，此后 LLM 全部失败。
**结果本身很有价值**：21 条用例自动降级到固定管线，用户侧依旧拿到正确答案，
验证了第 1 期的预算与降级兜底确实可用。新增 `llm_downgraded` 指标，
把"模型挂了"与"Agent 答不好"在指标层面区分开。

它还暴露了一个隐藏依赖：有 3 条意图用例原本靠 LLM 兜底才判对
（`我现在处于什么环节`、`帮我改一下面试时间`、`我想换个面试站点`）。
补规则后恢复到 100%，**intent 模式平均耗时从 434ms 降到 53ms**——
规则能覆盖的就不该依赖模型，这既省成本也少一处故障点。

## 5. 第 3 期：记忆与个性化（已完成）

### 5.1 要解决的问题

多轮对话里，用户第二轮几乎不会重复主题词：

```
用户：体检资料有什么要求？
助手：需上传指定级别医院的体检报告……
用户：那这个要多久能出结果          ← 没有主语，下游只能靠猜
```

后果有两层：意图识别拿到一句没主语的话；`knowledge_search` 拿它去检索也检不到东西。
同时画像注入是 `json.dumps` 一把梭（`{"name":"张三","site":"..."}`），模型读得到但用不好。

### 5.2 做法

**① 新增 `context` 节点（图的第一个节点）**：画像、历史召回、指代还原、重复问检测
一次算完写进 `context_block`，后续节点复用。为什么要集中：历史召回要走一次 Embedding，
若每个节点各查一遍，回炉重答时用户要为同一个问题多等好几秒。

**② 追问指代还原 `coref.py`**：纯规则，零模型调用。

| 触发条件 | 例子 | 处理 |
|---|---|---|
| 指代词开头 | 那/这/这个/还有/然后 | 剥掉指代词，主题前置 |
| 纯疑问谓语 | 还要多久 / 什么时候能弄好 | 主题前置 |
| 极短追问 | ≤6 字且无实体词 | 主题前置 |

主题来自 `memory.extract_topic`：**截到第一个谓语/疑问词**
（`体检资料有什么要求` → `体检资料`，`网签怎么操作` → `网签`）。
刻意不用模型改写：多一次调用延迟翻倍；改写结果不受控，评测无法归因；这类表达模式高度固定。

还原后同步替换最后一条 `HumanMessage`（保留"用户原话"附注），并在 system 里说明
"承接上文 X，实际要问的是 Y"，让意图 / 规划 / 工具调用站在同一起点上。

**③ 画像可读化** `memory.profile_block`：

```
候选人：张三｜投递岗位：产品岗（武汉站）｜当前环节：已初筛通过
毕业院校：某某大学 · 计算机
最近关注：体检资料、网签
```

**④ 重复提问收敛**：与上一轮相似度 ≥0.85 判为重复，提示"简明重述要点 +
追问是否需要更详细说明或转人工"，避免把长答案照抄一遍。

### 5.3 评测怎么验真

新增 4 条**带上一轮上下文**的用例（`cases.jsonl` 里带 `prev` 字段，只在 agent 模式跑）：

| # | 上一轮 | 本轮追问 | 还原结果 | 断言 |
|---|---|---|---|---|
| 34 | 体检资料有什么要求？ | 那这个要多久能出结果 | 体检资料要多久能出结果 | expect_resolved |
| 35 | 网签怎么操作？ | 还要多久 | 网签还要多久 | expect_resolved |
| 36 | 面试资料包括哪些？ | 还有呢 | 面试资料 | expect_resolved |
| 37 | 体检资料有什么要求？ | 体检资料有什么要求 | —— | expect_repeat |

`expect_resolved` 要求不仅答对，还必须真的触发了指代还原（`referent` 非空），
否则这条用例证明不了能力确实生效。

评测侧配套改动：每条用例从干净状态起步（清历史 + 清向量记忆），
并首次补了"记录用户本轮消息"这一步——线上由 `service.sse_chat` 负责，
评测原先没复刻这个时序，导致多轮用例一开始完全取不到上一轮。

### 5.4 第 3 期第 3 期踩到的坑

| 坑 | 现象 | 修法 |
|---|---|---|
| Judge 变成每条必调 | 为了"不影响放行"改成放行前总调用一次，结果 37 条里 35 条都在等模型，P95 冲到 37.7s | 恢复按需：只有规则已判 partial/fail 才调 Judge 复核 |
| 自己生成的工单号被当编造数字 | out_of_scope 的转人工答复包含工单编号，硬信息比对把它算成"无据数字" → 判 fail | 白名单必须同时喂给**硬信息比对**（原本只喂了隐私红线，等于没生效），并把 `create_ticket` 返回的 ticket_id 加进去 |
| `apply_judge` 缺 else 分支 | Judge 未调用且规则判 pass 时 status 根本没赋值 → 全量 `KeyError('status')` | 补兜底分支；教训是抽函数后没重跑单测就去跑全量评测 |
| 还原后的追问被判成查进度 | "体检资料要多久能出结果"被 LLM 判 progress_query → 路由到 get_my_progress，答非所问 | `keep_after_coref`：有指代锚点且不含第一人称诉求时，把 progress_query 纠回 kb_qa |
| 评测口径与图不一致 | 评测侧独立调了一次 `classify`，拿不到指代上下文，出现"图里走对了、指标判错"的假失败 | 以图最终采用的意图为准（run_agent 新增返回 intent） |
| 每条用例都清向量记忆 | Qdrant 本地库带文件锁，37 条各 scroll/delete 一次造成严重锁竞争，单条被测到 22 分钟 | 向量记忆只在整轮结束统一清；多轮用例（会 recall 历史）才单独清 |
| 字面 must 匹配过严 | 模型把"留下手机号"同义改写成"留下联系方式"，用例就判缺关键事实 | 关键事实改成抓**要做的动作**（`留言`/`重新发送`），而不是原文里的某个词 |

### 5.5 第 3 期评测结果

| 模式 | 用例 | 通过率 | 意图 | 事实 | 引用 | 工具序列 | 转人工 | 降级 | 平均 | P95 |
|---|---|---|---|---|---|---|---|---|---|---|
| intent | 30 | 100% | 100% | — | — | — | 100% | 0 | 46ms | 8ms |
| fixed | 30 | 100% | 100% | 100% | 100% | — | 100% | 0 | 15ms | 23ms |
| agent | 37 | 94.6% | 100% | 100% | 100% | 100% | 100% | 0 | — | — |

agent 那一行是模型健康时（eval 期间无 4xx）的实测：35/37，两条例外的根因都是标注字面过严，
已按 §5.4 最后一条修正，但**修正时尚未来得及复跑确认**——紧接着模型账号就进入
间歇 `400 Access denied, account not in good standing`，之后所有请求被拒，
后续两轮跑出来的 agent 结果（`llm_downgraded` = 11、37）**不可作为能力基线**，已弃用。

多轮能力本身已确认生效：`coref_hits = 3`（#34 #35 #36 全部触发还原，
如 `网签还要多久`）、`repeat_hits = 1`（#37 正确识别重复提问）。

这也侧面印证了一件事：**外部模型不可用时，Agent 会 100% 降级到固定管线，用户照样拿到回答**。
`llm_downgraded` 这个指标让"模型挂了"和"Agent 答不好"在指标上可区分，不会被误读成能力退化。

## 6. 怎么跑

- 界面：超管登录 → 【评测回归】→ 选模式 → 运行评测（历史记录可对比）
- 命令行：

```bash
cd app
python -c "import sys; sys.path.insert(0,'.'); from agent import eval as E; print(E.run('fixed')['summary'])"
```

> 注意：Qdrant 本地库带文件锁，**跑命令行评测前必须先停掉 uvicorn**，否则报 `.lock Permission denied`。
