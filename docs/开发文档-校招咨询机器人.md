# 校招咨询机器人 · 开发文档（V0.1 草案）

> 更新日期：2026-10-24
> 状态：需求与架构规划阶段
> 关联文档：《功能规划 V0.2 — 候选人端 + HR 后台》（产品定位已升级为双端平台，功能细化见该文档）

## 1. 项目定位

面向**校招执行团队（领队 + 基地人力 + 专业面试官）**的流程辅助机器人，解决校招站点执行过程中"流程长、环节多、靠 Excel 和群消息人肉跟踪"的问题。

机器人的三类核心价值：

1. **流程导航（咨询）**：任何人问"下一步该干嘛 / 这个环节谁负责 / 卡在哪儿了"，机器人基于当前站点状态给出准确回答。
2. **流程驱动（提醒与跟踪）**：按站点维度自动推进状态，超时预警（如"学生未按约定时间面试 → 面试官需在次日 24:00 前自行补约"）。
3. **资料与事务代办**：短信通知、面试/体检资料收集与审核跟踪、各类名单（意向沟通名单、录用表、offer 发放表、录用资料表）的生成辅助。

**不做的事**（边界）：
- 不替代格慧招：测评发起、面试排期仍在格慧招操作，机器人只做**跟踪与提醒**（除非后续拿到格慧招 API/确认可对接）。
- 不替代网签系统：网签、三方盖章仍走原系统，机器人只做**应约状态跟踪提醒**。
- 不做 AI 自动决策录用：筛选、录用由人决定，机器人只提供信息整理。

## 2. 业务流程拆解

两条流程 90% 重合，差异集中在**面试环节的形式**。先抽象出统一的状态机，再按站点类型挂载差异节点。

### 2.1 统一状态机（站点 × 学生双维度）

**站点级节点**（领队操作为主）：

| # | 节点 | 责任人 | 机器人可做的事 |
|---|------|--------|----------------|
| S1 | 宣讲 | 领队 | 宣讲材料/常见问题问答 |
| S2 | 简历初筛 | 领队 | 简历汇总、按硬性条件（学校/专业/学历）预筛辅助 |
| S3 | 发起测评 | 领队（格慧招操作） | 从初筛名单生成格慧招操作清单、跟踪测评完成率 |
| S4 | 收集面试官会议信息（仅非面试站点） | 领队 | 收集各单位专业面试官的腾讯会议号 + 可用时间段，结构化入库 |
| S5 | 安排初面 | 领队（格慧招排期） | 非面试站点：按面试时间+会议号生成排期表；面试站点：酒店线下排期跟踪 |
| S6 | 安排复试 | 领队（格慧招排期） | 跟踪复试完成情况 |
| S7 | 通知上传面试资料 | 领队/机器人 | **自动发短信** + 跟踪上传状态，未上传者定时催办 |
| S8 | 面试资料审核 | 基地人力 | 审核清单勾选、驳回原因记录、自动通知补传 |
| S9 | 意向沟通名单 | 领队 | 一键从"资料审核通过"学生生成名单 |
| S10 | 意向沟通会 | 领队 | 会议通知、签到跟踪 |
| S11 | 体检资料上传与审核 | 学生/基地人力 | 同 S7/S8 逻辑复用 |
| S12 | 录用表报领导 | 领队 | 两资料均审核通过的学生自动汇入录用表模板 |
| S13 | offer 发放表 | 领队 | 模板生成 |
| S14 | 发起网签 | 领队（网签系统） | 跟踪发起状态 |
| S15 | 学生应约跟踪 | 机器人 | **定时查网签系统/人工录入**，未应约超时提醒（时效敏感） |
| S16 | 三方盖章返邮 | HR/行政 | 邮寄状态跟踪 |
| S17 | 维护三方录用信息表 + 录用资料表 | 领队 | 汇总生成，收官核对清单 |

**学生级状态**（挂在站点状态机下）：
`已初筛通过 → 测评中/已通过 → 已约初面 → 初面通过 → 已约复试 → 复试通过 → 待传面试资料 → 资料审核中/驳回 → 意向沟通完成 → 待传体检资料 → 体检资料审核通过 → 待录用审批 → 已发 offer → 网签中/已应约 → 三方已回收 → 已归档`

### 2.2 两类站点差异点

| 环节 | 非面试站点 | 面试站点 |
|------|-----------|----------|
| 初面形式 | 腾讯会议线上（面试官自己面） | 酒店线下 |
| 前置动作 | 需先收集面试官会议信息 | 无 |
| 学生改期 | 学生无法按约定时间 → 面试官自行联系，**最迟不超过面试次日**（机器人重点盯这个 SLA） | 一般现场解决 |
| 复试 | 格慧招安排，基地人力线上/线下 | 酒店线下 |

## 3. 功能规划（MVP → 完整版）

### Phase 1（MVP）：流程看板 + 咨询问答
- 站点/学生双维度的流程看板（替代 Excel）：每名学生当前所处环节、停留时长、负责人。
- 规则问答机器人：输入站点/学生名 → 回答"当前环节、下一步、负责人、SLA"。
- 面试站点的线下流程全量跟踪。
- 形态建议：企业微信/飞书群机器人 + 简单 Web 看板。

### Phase 2：提醒引擎 + 资料收集
- 超时预警：学生改期未补面（>1 天）、资料未上传（N 天催办）、网签未应约（每天提醒）。
- 短信自动发送（对接短信服务）+ 上传链接，学生上传面试/体检资料到系统。
- 审核工作台：资料审核通过/驳回（驳回原因模板化），驳回自动触发补交通知。

### Phase 3：名单/表格自动生成
- 一键生成：意向沟通名单、录用表、offer 发放表、三方录用信息表、录用资料表（按公司现有模板输出 Excel）。
- 数据导出与站点复盘报表（各环节转化率、平均耗时）。

### Phase 4（可选，依赖外部条件）：深度对接
- 格慧招排期联动（需确认有无 API，或确认是否可接受 RPA/人工录入）。
- 腾讯会议 API 自动建会（收集面试官时间段后自动排会+发会议号）。
- 网签系统应约状态自动拉取（需系统方支持，否则退化为人工录入+机器人催办）。

## 4. 技术架构建议

```
┌─────────────────────────────────────────────┐
│  交互层：企业微信/飞书群机器人 · Web 看板      │
├─────────────────────────────────────────────┤
│  业务层（核心）                              │
│   · 状态机引擎（站点流程 + 学生流程双轨）      │
│   · 规则/SLA 引擎（超时预警、催办策略）        │
│   · 问答服务（LLM + 流程知识库 RAG）          │
│   · 文档生成（模板填充 → Excel/Word）         │
├─────────────────────────────────────────────┤
│  集成层（按条件逐步启用）                     │
│   短信网关 · 腾讯会议 API · 格慧招 · 网签系统  │
├─────────────────────────────────────────────┤
│  数据层：PostgreSQL（站点/学生/资料/审计日志） │
│  对象存储：面试资料、体检资料、简历            │
└─────────────────────────────────────────────┘
```

技术选型建议（供讨论）：
- **后端**：Python (FastAPI) —— 便于接 LLM、处理文档；状态机用显式枚举 + 迁移表，不搞隐式流转。
- **问答**：LLM + RAG（流程 SOP 文档 + 当前站点状态注入上下文），宁可答"这个要去问领队 XX"，不允许编造。
- **部署**：公司内网或私有云，学生资料属个人信息，注意《个人信息保护法》合规（加密存储、最小留存、脱敏展示）。

### 关键数据模型（初稿）

- `site`（站点：类型/地点/宣讲日期/领队）
- `student`（学生：基本信息/院校专业/联系方式）
- `application`（学生×站点：当前状态/各环节时间戳/负责人）
- `interview`（初面/复试：形式/时间/面试官/会议号/结果/改期记录）
- `document`（资料类型/上传状态/审核状态/驳回原因）
- `sla_rule`（环节超时规则）/ `notification_log`（短信/提醒记录，审计用）

## 5. 待确认问题（影响方案的关键决策点）

1. **机器人载体**：企业微信群机器人？飞书？还是独立网页？（决定交互层与 API 可用性）
2. **格慧招**：是否有 API 或导出能力？没有的话排期数据靠人工录入还是 RPA？
3. **网签系统**：应约状态能否自动获取？还是每天人工查+录入？
4. **短信通道**：公司现有短信平台是什么？发学生个人手机号需确认合规授权。
5. **使用者规模**：几个站点并行？决定是单机小工具还是正经服务端。
6. **资料审核标准**：面试/体检资料的审核 checklist 是否有现成文档（这是 RAG 知识库的核心语料）。

## 6. 可参考的开源项目（GitHub 调研结果）

### 高度相关（国内场景、可直接借鉴架构）

| 项目 | 亮点 | 对本项目的参考价值 |
|------|------|-------------------|
| **libz-renlab-ai/AgenticHR** | AI 驱动招聘助手：简历自动采集（Boss直聘）→ AI 筛选打分 → 读飞书日历避冲突排面试 → **自动创建腾讯会议** → 飞书通知。开源自托管、完全免费 | ⭐ 最接近：同样是国内"排面试+腾讯会议+IM 通知"链路，腾讯会议自动化和日历避冲突的实现可直接参考 |
| SrinivasBathula9/ai-candidate-screening-process | 多 Agent 分工（技术筛选/沟通/排期协调）模拟招聘团队，Streamlit + Zoom API | 多 Agent 角色划分思路可借鉴（对应领队/人力/面试官多角色） |

### 结构参考（成熟 ATS 流程设计）

| 项目 | 亮点 | 参考价值 |
|------|------|---------|
| chamals3n4/OpenATS | 开源 ATS：候选人流水线看板、**面试排期（候选人选时间段+日历同步）**、打分权重、offer 模板、邮件模板、完整技术栈（Next.js + Express + PostgreSQL + BullMQ） | 状态机+看板+排期+模板化的整体设计范本，BullMQ 任务队列做法适合做催办/提醒引擎 |
| owenstuckman/luma | 多租户面试排期系统，按候选人与面试官双方空闲时间自动排期（400+ 人规模实战） | "面试官可用时间收集 → 自动排期"正是非面试站点 S4/S5 的核心难题 |
| Harly（harly.dev，MIT） | 自托管 ATS：AI copilot（可执行动作：审简历、挪阶段、发邮件）、候选人自助门户、电子签 | 学生自助上传资料/查状态的"候选人门户"思路；AI copilot 的操作审计日志设计 |
| Shubham-Dash2004/AI-HR-Agent / adn26/HR-assistant | 简历解析 + JD 匹配打分 + Google Calendar 排期 + 邮件生成 | 简历解析→打分的轻量实现；**所有外部依赖都有降级方案**（API 不通就给预填链接）的容错设计值得学 |

### 结论
没有找到与"校招站点执行 + 格慧招 + 网签"完全对口的开源项目（这部分是公司私有流程），但 **AgenticHR + OpenATS 两个项目组合起来，覆盖了本项目约 60% 的通用能力**（排期、会议、通知、看板、状态机）。建议：业务流程引擎自研（贴合公司状态机），集成层（腾讯会议 API、IM 通知、任务队列）直接参考/复用上述项目的实现。
